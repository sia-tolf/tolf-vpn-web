## 1. Назначение и границы системы

TOLF Network Suite объединяет защищённое подключение и региональный выбор сети. Пользователь может подключиться через IKEv2 или экспериментальный AnyConnect/OpenConnect, пользоваться Smart DNS отдельно от VPN, выбирать маршрутизацию и управлять доступом из личного кабинета. Важно не смешивать четыре разных понятия:

1. **Вход VPN** — место завершения туннеля клиента: Рига или Москва.
2. **Выход трафика** — регион, через который сервер отправляет пакет к конечному адресу.
3. **DNS-маршрут** — резолвер и upstream для имени; он не обязан совпадать с выходом пакета.
4. **Управление** — аккаунты, политика, сертификаты и API на UK; региональные узлы передают трафик и применяют полученную политику.

Вариант Smart DNS для VPN должен сосуществовать с прежним, классическим DNS-режимом. Переключатель между ними является требованием проекта; нельзя объявлять Smart DNS единственным DNS для всех VPN-клиентов.

### 3.1. Таблицы и метки маршрутизации

Историческая схема использует московский `main` для локального российского выхода, таблицу `100` для маршрута через Ригу, таблицу `101` для отдельных направлений через Челябинск; метки `0x100`, `0x200`, `0x400` выбирают соответствующие направления. Рижские правила для её пулов и таблица `102` направляют часть трафика к Москве. Фактический приоритет `ip rule` и маршрут возврата нужно всегда читать вместе с `nft list ruleset` и `ip route show table ...`.

Для пилота AnyConnect на Москве текущий `/usr/bin/tolf-oc-mode` формирует отдельную цепочку `inet fw4 tolf_oc_mode`, работающую в `prerouting` с приоритетом `mangle - 1`. Действующее состояние записывается в `/etc/tolf-oc-mode`, runtime в `/tmp/tolf-oc-mode`, а постоянная цепочка в `/etc/nftables.d/97-tolf-oc-mode.nft`. При смене режима удаляется conntrack для `10.21.0.0/24`, чтобы уже установленные потоки не продолжали старый путь. Указанный в прежней проверке MSS 1200 относится к отдельным правилам, а не к выбору режима.

### 3.2. Маршруты AnyConnect

| Режим UI | Режим API | Путь из `10.21.0.0/24` | Реализация на Москве |
|---|---|---|---|
| Авто | `auto` | RU → Москва; остальное → Рига | Сначала mark `0x200`, адреса из `@ru4` и `@ru_domains4` получают `0x100`. |
| RU | `ru` | Весь трафик → Москва | Для пула не устанавливается перенаправляющая цепочка; используется `main`. |
| LV | `lv` | Весь трафик → Рига | На все пакеты пула ставится `0x200`. |
| YT | `yt` | RU и YouTube → Москва; остальное → Рига | Общий `0x200`, возврат `0x100` для `@ru4`, `@ru_domains4`, `@yt_domains4`. |

Управление этими режимами сейчас **пилотное и общее для `pilot-tolf`**, а не полноценная независимая политика каждого пользователя. Это следует непосредственно из таблицы `oc_user_mode` и жёстко указанного имени в `tolf_oc_policy.py`. Надпись `user0_ipad` в личном кабинете относится к VPN-доступу аккаунта и сама по себе не доказывает, что текущий AnyConnect-туннель использует это имя. До персонализации нельзя распространять пилотную политику на других пользователей как отдельную настройку.

## 4. IKEv2: профили и пути пакетов

IKEv2 завершается на выбранной точке входа. Клиент отправляет в неё трафик по назначенным маршрутам; **Local ID** и соответствующий пул определяют дальнейший путь на сервере. Желаемые CHILD_SA: общий трафик и отдельный локальный `192.168.0.0/16`, чтобы домашняя сеть оставалась доступной через соответствующий маршрут. Фактическое согласование traffic selectors нужно проверять на устройстве и через `swanctl --list-sas`.

| Вход и профиль | Ожидаемое поведение |
|---|---|
| Рига `ru`, пул `10.15/24` | Трафик через межсерверный туннель к Москве, российский выход. |
| Рига `sr`, пул `10.16/24` | RU через Москву; прочее возвращается в Ригу и выходит там. |
| Рига `ch`, пул `10.17/24` | Выбранные российские направления через Москву к Челябинску; прочее через Ригу. |
| Москва, пустой/обычный Local ID | Российские адреса через Москву; прочее через Ригу. |
| Москва `ru`, пул `10.11/24` | Весь трафик через Москву. |
| Москва `lv`, пул `10.12/24` | Весь трафик через Ригу. |
| Москва `sr`, пул `10.13/24` | Московский маршрут по умолчанию с выделенными сервисами через Ригу. |

Генератор Apple выдаёт `.mobileconfig` с типом `com.apple.vpn.managed`, `VPNType=IKEv2`, именем сервера как Remote Identifier, EAP-учётными данными и настройками DNS/On Demand. Проектные алгоритмы: AES-256-CBC, SHA2-256, MODP-2048/DH14; MOBIKE и DPD должны работать в связке клиента и сервера. Android получает `.sswan` для strongSwan VPN Client; On Demand в этом формате не настраивается. Эти параметры документированы по коду прежнего снимка и должны сверяться в свежем сформированном профиле.

Выдача и подпись Apple-профилей: на UK создан корневой `TOLF Root CA` и сертификат `TOLF Profile Signing`; DER корневого CA опубликован через `config.tolf.is`. CMS-подпись проверялась; iOS показывает «Signed by TOLF Profile Signing», но не обязательно «Verified». Сроки и пути текущих сертификатов проверяются на UK, сами приватные ключи не копируются в документацию.

## 5. AnyConnect/OpenConnect: пилот и статус

Пилот использует ocserv и сертификат клиента `TOLF OC Client CA`; имя пользователя берётся из CN (`cert-user-oid = 2.5.4.3`). На iOS проверялся Cisco AnyConnect с DTLS; соединение с сертификатом без ввода отдельного пароля удалось. Для московского пилота сокет управления — `/var/run/occtl-moscow.socket`, клиентский пул — `10.21/24`. Команда без `-s` ошибочно ищет `/var/run/occtl.socket`.

Управляющая последовательность для выбора режима:

1. `vpn.tolf.is` отправляет `POST` на `https://api.tolf.is/oc-test/policy`. Тело JSON содержит поле `mode` со значением `auto`, `ru`, `lv` или `yt`.
2. UK-модуль `/opt/tolf-api/tolf_oc_policy.py` проверяет формат, запускает SSH с фиксированным known_hosts и командой `tolf-oc-mode <mode>`.
3. Московский forced-command `/usr/bin/tolf-oc-remote` принимает только четыре режима, вызывает `/usr/bin/tolf-oc-mode`, возвращает `{"status":"ok","mode":"..."}`.
4. UK фиксирует `mode` и `revision` в SQLite `oc_user_mode` для `pilot-tolf`; `auto` удаляет override. Ответ содержит `username`, `mode`, `revision`, `applied`.

**Порядок применения:** Москва применяет правила до фиксации записи в UK. Если промежуточный этап оборвётся, надо сравнить `/etc/tolf-oc-mode`, таблицу `oc_user_mode` и ответ GET; один ответ браузера не заменяет проверку фактической цепочки.

Проверка зелёной точки:

1. Сайт получает сохранённый режим через `GET /oc-test/policy`.
2. Пока вкладка AnyConnect открыта, `js/transport-selector.js` опрашивает `GET /oc-test/session` каждые 10 секунд и при возврате вкладки.
3. UK через SSH выполняет разрешённую команду `tolf-oc-session pilot-tolf`.
4. Московский шлюз проверяет доступность `ocserv` и вызывает `occtl -s /var/run/occtl-moscow.socket --json show user pilot-tolf`. У подключённого пользователя ожидается exit code 0; для отключённого фактически наблюдался `[]` и code 2.
5. UK возвращает режим из БД и boolean `connected`. Сайт зажигает зелёную точку только у выбранного режима, если `username=pilot-tolf`, `mode` совпал и `connected=true`. Ошибка API или отсутствие сессии гасит точку.

**Проверено 01.10:** при отсутствии сессии API вернул `{"connected":false}`. При подключении получен ответ:

```json
{"username":"pilot-tolf","mode":"lv","revision":4,"applied":true,"connected":true}
```

Автоматические проверки фронтенда покрыли disconnected, connected и ошибку API; окончательная визуальная проверка на пользовательском устройстве остаётся отдельной точкой.

Зелёная точка подтверждает наличие **серверной сессии пилота**, а не доставку конкретного пакета до сайта, не качество DNS и не личную сессию пользователя `user0_ipad`. Масштабирование требует персональной связки аккаунт ↔ сертификат/CN ↔ политика ↔ сессия и авторизованного API; нынешние `/oc-test/*` являются пилотными маршрутами.

## 6. TOLF Smart DNS

Smart DNS — самостоятельный модуль, доступный зарегистрированному пользователю без обязательного VPN. Он принимает зашифрованные запросы DoH/DoT, проверяет учётные данные и выбирает upstream по политике домена и региона. **UK хранит аккаунты, credentials, политику, измерения и управление**; региональные узлы выполняют DNS-трафик.

Из обсуждённого развёртывания рижского data plane:

| Сервис/адрес | Роль |
|---|---|
| `tolf-smart-unbound`, `127.0.0.1:5353` | рекурсор/пересылка по выбранным upstream. |
| `tolf-dnsdist`, `127.0.0.1:5453` | распределение DNS-запросов. |
| `tolf-doh-backend`, `127.0.0.1:18081` | HTTP backend для DoH. |
| `dns.tolf.is` → nginx → `127.0.0.1:18081` | публичная точка DoH. |
| `/etc/tolf-dns/node.env` | конфигурация узла и секрет синхронизации; значения не документируются. |

Серия политик `ecs1` валидируется для узла `riga`. На UK обсуждены маршруты API `/dns/node/health`, `/credentials`, `/smart-policy`, `/measurement-targets`, `/measurements`, `/usage`; фактические HTTP-префиксы, методы и схема ответа каждого маршрута должны подтверждаться свежим кодом API. Типовые upstream-группы: `local`, `russia`, `quad9_ecs`. В интерфейсе пользователь должен понимать, какой DNS применён к заданному домену и почему; это требование к диагностическому инструменту Domain/DNS Route Check.

У VPN-пользователя должны быть **два режима**: существующий классический DNS VPN и новый Smart DNS. Переключение требует корректного обновления профиля/настройки клиента и теста разрешения имён. Windows 10 и Android требуют отдельной установки клиента и его обслуживания; идея Microsoft Store и автоматических обновлений пока не равна завершённому релизу.

## 7. Веб-сайты и пользовательские сценарии

### 7.1. Главный сайт `tolf.is`

Репозиторий `sia-tolf/tolf-is`: `index.html` содержит страницу, `app.js` управляет UI, `account-state.js` синхронизирует отображение входа, `styles.css` и общие `tolf-buttons`, `tolf-header`, `tolf-ui` задают визуальную систему; `tolf-logo-star.svg` и `tolf-wordmark.*.js` отвечают за знак и написание TOLF. Код этого сайта хранится отдельно от VPN-портала. Главная направляет к VPN, DNS и личному кабинету; конкретные URL переходов надо проверять по текущему `index.html` при изменении навигации.

### 7.2. Страницы `vpn.tolf.is`

| Путь | Что видит пользователь и что делает страница |
|---|---|
| `/` | «Мой VPN»: платформа iOS/Android/Windows, выбор IKEv2/AnyConnect, точка входа, настройки профиля, обзор доступа, маршрутизация, измерения. |

Текущий дизайн намеренно нейтральный и похож на системный iOS: поля и кнопки согласованной высоты, подписи обычного начертания, переключатель языка высотой 42 px. Страницы должны проверяться отдельно на широком iPad и узком iPhone, включая длинные локализованные строки.

### 7.3. Экран «Мой VPN» по порядку

1. **Выбор платформы.** `iOS`, `Android`, `Windows` меняют инструкции и доступную доставку. Этот выбор не подключает VPN самостоятельно.
2. **Выбор протокола.** `IKEv2` показывает генератор профиля. `AnyConnect` выбирает московскую точку входа пилота; рижский выбор IKEv2 сохраняется при возврате. Строка обзора показывает слева «Протокол», справа `IKEv2` или `AnyConnect`. Это описание выбора, не индикатор подключения.
3. **Точка входа VPN.** Рига и Москва имеют отдельные измерения задержки и рекомендацию; ограничение доступности зависит от аккаунта/промокода. При AnyConnect пилоте отображается Москва.
4. **Настройки VPN.** Local ID, DNS, Apple profile name, On Demand и дополнительные правила видны в раскрываемом блоке в зависимости от платформы.
5. **Маршрутизация AnyConnect.** `Авто` и три сегмента `RU/LV/YT`; две строки пояснения показывают фактический маршрут. После выбора POST сохраняет режим на UK и применяет его на Москве; выбранная кнопка и зелёная точка имеют разные значения (выбор против активной сессии).
6. **Профиль и действия.** Создать доступ, сформировать профиль, установить или поделиться `.mobileconfig`, скопировать ссылку, открыть QR, сменить пароль VPN или удалить доступ. Смена пароля требует нового профиля на устройстве.
7. **Проверка соединения.** Браузерный LibreSpeed показывает RTT, джиттер, загрузку и отдачу до выбранного тестового сервера. Это измерение HTTPS-пути браузера, а не автоматически проверка работающего VPN-туннеля.
8. **Сеть TOLF.** Межсерверные метрики приходят из `/network-metrics`; их нельзя трактовать как скорость конкретного iPad.

### 7.4. Модели состояния интерфейса

| Надпись или индикатор | Точное значение |
|---|---|
| «Протокол — AnyConnect» | Выбран тип интерфейса на сайте. |
| Выбранный сегмент `RU/LV/YT/Авто` | Отображён текущий выбранный режим; GET после обновления загружает сохранённое значение UK. |
| Зелёная точка сегмента | Подтверждена активная серверная сессия пилота для того же режима. |
| Погашенная точка | Сессия не обнаружена, данные не загружены или API временно недоступен; без отдельного сообщения это не диагноз причины. |
| «Сохранено» / ошибка сохранения | Результат изменения политики; не доказательство VPN-сессии. |
| «Готово» у измерений | Тест ожидает запуска, а не сообщает о подключении VPN. |

## 9. Серверные модули и установка

### 9.1. UK API

`/opt/tolf-api/main.py` регистрирует HTTP маршруты и интеграции. `tolf_oc_policy.py` — проверенный 01.10 пилотный модуль OpenConnect: SQLite `oc_user_mode`, строгий JSON `mode`, SSH c pinned host key, управление московским узлом, GET policy и GET session. Скрипты `setup/*` в репозитории — установщики и шаблоны; наличие файла в GitHub не доказывает, что та же версия запущена на UK. Для каждой установленной подсистемы нужна таблица: файл в Git, установленный путь, способ регистрации в `main.py`, unit, версия и контрольная проверка.

| Группа в `setup/` | Роль |
|---|---|
| `admin/` и `admin/nodes/` | Админ API, инвентарь IKEv2-сеансов и узлов, gateway read/control, ограниченные тестовые действия. `session_reader.py` относится к strongSwan, не к московскому ocserv-сокету пилота. |
| `invitations/` | Приглашения, проверка и привязка VPN-доступа, передача на рижский узел. |
| `password-auth/` | Дополнительный вход на сайт по паролю и правила совместимости с Passkey. |
| `quick/` | API быстрой первоначальной настройки. |
| `personal-routing/` | Хранение персональных правил, группы доменов, доставка политики на узел, gateway и отдельный user0-сервис. |
| `routing/` | Установка/обновление режима YouTube по спискам адресов. |
| `windows/` | Windows API и клиентская маршрутизация; native-код приложения хранится в `setup/windows/native/`. |

### 9.2. Москва: AnyConnect control и data plane

`/usr/bin/tolf-oc-remote` — forced-command для ключа UK. Он принимает фиксированные `tolf-oc-mode auto|ru|lv|yt` и `tolf-oc-session pilot-tolf`; произвольную команду отвергает. `/usr/bin/tolf-oc-mode` пересоздаёт runtime nft-цепочку, сохраняет состояние на диск и при смене режима очищает соединения пилотного пула. `occtl -s /var/run/occtl-moscow.socket` читает фактические AnyConnect-сеансы. Команда `occtl` без явного `-s` проверяет другой сокет и может ложно создать впечатление, что ocserv не работает.

### 9.3. Рига: IKEv2, классический DNS и Smart DNS

Исторические конфиги: strongSwan `swanctl` в `/etc/swanctl/conf.d/`, Unbound на `10.254.0.53`, межсерверный `awgmoscow`, policy routing и nftables. Smart DNS содержит отдельные `tolf-smart-unbound`, `tolf-dnsdist`, `tolf-doh-backend`; не следует подменять их прежним резолвером профилей. Для каждого сервиса нужно фиксировать слушающий адрес, systemd unit, upstream, сертификат и путь логов после свежей инвентаризации.

## 11. Учётная запись, безопасность и границы ответственности

- Аккаунт сайта, VPN EAP-доступ IKEv2, AnyConnect сертификат и Smart DNS credential — разные объекты. Интерфейс должен явно указывать, что именно создано, отозвано или сменено.
- Passkey защищает вход на сайт; подтверждение Passkey не означает, что на устройстве установлен VPN-профиль.
- VPN-пароль IKEv2 может требовать переустановки профилей на всех устройствах после смены.
- Пилотный AnyConnect использует сертификат клиента и фиксированное имя `pilot-tolf` в маршрутизаторе; пользовательские AnyConnect сертификаты/политики нуждаются в отдельном реестре.
- UK остаётся control plane. Рига и Москва принимают только ограниченные служебные операции через SSH gateway; в браузер не передаются SSH-ключи и конфигурация узлов.
- Состояние `connected:true` пилота является информацией о московском сервере. Перед массовой выдачей нужно авторизовать этот endpoint и привязать ответ к конкретному аккаунту/устройству.
- Админ API проверяет права на сервере, включая отзыв доступа, а аудит фиксирует действия. Показ кнопки в UI не заменяет проверки на API.

## 12. Диагностика по слою отказа

| Симптом | Проверка в первую очередь | Как отличить причины |
|---|---|---|
| Страница не открывается | DNS имени, HTTPS, GitHub Pages/UK API, ошибки браузера | Проверка IP без верного Host/SNI может дать ожидаемую 404. |
| Выбор режима не сохраняется | POST/GET `/oc-test/policy`, SSH UK → Москва, `/etc/tolf-oc-mode`, nft-цепочка | API `applied:true` и фактические правила должны совпадать. |
| Точка не зеленеет | `/oc-test/session`, `occtl -s /var/run/occtl-moscow.socket --json show user pilot-tolf`, выбранный режим, видимость вкладки | Пустой список/exit 2 = нет сессии; 502/503 = ошибка проверки, не `false`. |
| VPN подключён, сайты не открываются | virtual IP, route/rule, marks/sets, conntrack, обратный маршрут, DNS, MTU/PMTU | Проверять один путь пакета и ответ; не начинать с гипотезы о CPU. |
| DNS не отвечает | режим DNS, локальный listener, авторизация Smart DNS, выбранный upstream, обратный путь | Классический `10.254.0.53` и `dns.tolf.is` — разные сервисы. |
| Малая скорость AnyConnect | TLS/DTLS, путь через домашний роутер и мобильную сеть, MTU/MSS, потери, ретрансмиты | Сравнивать одинаковый сервер/путь и направление. |
| IKEv2 висит на «Connecting» | UDP 500/4500, сертификат, EAP, DPD/MOBIKE, NAT, SA на сервере | Подключение в UI профиля и реальный CHILD_SA различаются. |
| Browser speedtest «готово», но нет цифр | HTTPS/8443, TLS, CORS, выбранный target, worker, upload/download endpoints | Это тест браузера до узла, не ocserv-сессия. |

Минимальные контрольные команды, которые не изменяют состояние:

```text
UK:      GET /oc-test/policy; GET /oc-test/session; статус tolf-api.
Москва:  occtl -s /var/run/occtl-moscow.socket --json show users;
         cat /etc/tolf-oc-mode; ip rule; nft list chain inet fw4 tolf_oc_mode.
Рига:    swanctl --list-sas; ip rule; ip route; состояние DNS units;
         тест имени через классический DNS и Smart DNS отдельно.
Клиент:  активный протокол/сервер, назначенный адрес, DNS, фактический egress IP.
```

`ip rule` из 29.08 приведены с приоритетами, поскольку порядок меняет результат:

```text

8986:   from 10.15.0.0/24 lookup main
```

Для ответа клиентам Риги в `main` требовались маршруты `10.15/16/17.0.0/24 dev awgriga`. Списки `ru4` (российские IP) и `ru_domains4` (IP российских доменов) выбирали российский путь. Снимок также упоминал `ee_domains4`, `ee_ips4`, `rf_direct4`. Новый режим `yt` в цепочке `tolf_oc_mode` использует `yt_domains4` и обрабатывает только источник `10.21.0.0/24`.

Пилотная цепочка `inet fw4 tolf_oc_mode` создаётся в `prerouting` с приоритетом `mangle - 1`, сначала задаёт mark `0x200` для `auto/lv/yt`, затем переопределяет его на `0x100` для специальных назначений. Режим `ru` не добавляет пометку в этой цепочке. Скрипт при применении удаляет правило `from 10.21.0.0/24 lookup 100`, пересоздаёт цепочку, сохраняет её в `/etc/nftables.d/97-tolf-oc-mode.nft` и пишет режим в `/etc/tolf-oc-mode`. **Проверять совместно** активные `ip rule`, маршруты таблиц `main/100`, nft-цепочку и actual conntrack: одного содержимого файла недостаточно.

Исторический firewall OpenWrt `fw4` содержал зоны `lan`, `wan`, `wg`, `awg`, `awgout`, `office`, `riga`, `wgch`. В зоне `wan` masquerade для внешнего выхода, `riga` разрешала нужный межсерверный forwarding; `wgch` по умолчанию не пропускала произвольный forward. Специальный SNAT к `10.31.0.1` перед возвратом нероссийского трафика рижских `10.16/17` предотвращал повторное попадание под рижское source-rule. Перед выходом в `wgch` исходный адрес менялся на `10.32.0.1`; на Челябинске выполнялся окончательный NAT. Конкретные nft handles после reload нестабильны.
